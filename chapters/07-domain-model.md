# 第7章: トランザクションスクリプトとドメインモデル

> この章の軸: ②業務ロジックの置き方

## この章のゴール

業務ルールを「処理の流れの中」から「業務を表すオブジェクトの中」へ移します。トランザクションスクリプトとドメインモデルの違いと、使い分けの目安を体験で理解します。あわせて、値オブジェクト（Value Object）とリポジトリ（Repository）の考え方に触れます。

## Why: なぜロジックの置き方を学ぶのか

第2〜6章では、クラスの作り方を学びました。しかし、「そもそも業務ルールをどこに書くか」は、別の問題です。

これまでの神クラスは、1つのメソッドに上から下へ手続きを書く形でした。小さな処理なら、この形が最も読みやすく、速く書けます。しかし、ユースケースが増えて同じルールが複数の処理に現れると、ルールのコピーが増えます。

## 前提

[第6章](./06-template-method.md)を読み終えていること。第1章で学んだ「基本型への執着」という臭いを、この章で直します。

## 悪い実装を読む

次のファイルを開いてください。

- [TransactionScriptOrderProcessor.java](../src/main/java/com/example/orders/ch07_domain_model/before/TransactionScriptOrderProcessor.java)

このクラスは、処理を上から下へ手続きとして書く「トランザクションスクリプト」です。**この形は悪い設計ではありません。** 小規模な業務では、素直で読みやすい書き方です。

しかし、次の点に注目してください。

- 「在庫が足りるか」という業務ルールを知っているのは、`process` メソッドだけです
- 金額は `int` です。負の値や、割引が小計を超える値を、型は止めてくれません
- 在庫は `Map<String, Integer>` を直接操作しています。保存先が変わると、業務ルールの周りまで書き換えます

次の変更要求が来たら、どうなるでしょうか。

- 注文キャンセルの処理を足したい（在庫を戻す）
- 返品の処理を足したい（在庫を戻し、返金する）
- 在庫を、Mapでなくデータベースに持ちたい

在庫を操作する点は、どちらの処理も同じです。在庫のルールのコピーが、処理の数だけ増えます。

## 考え方

### トランザクションスクリプトとドメインモデル

ロジックの置き方には、大きく2つの流儀があります。

| 観点 | トランザクションスクリプト | ドメインモデル |
| :--- | :--- | :--- |
| 考え方 | 1つの処理を、1つの手続きとして書く | 業務の概念をオブジェクトにし、ルールをその中に持たせる |
| ルールの置き場所 | 処理の流れの中 | 業務オブジェクトの中（`Money`、`Stock`） |
| 向く規模 | 小規模。ルールが少なく、ユースケースも少ない | 中〜大規模。ルールが複雑で、複数の処理から使われる |
| 長所 | 速く書ける。処理の流れが一望できる | ルールが1カ所に集まり、重複しない。単体でテストしやすい |
| 短所 | ルールの重複が起きやすい | 設計に手間がかかる。小規模だと過剰になる |

### この章で作る部品

| 部品 | 種類 | 役割 |
| :--- | :--- | :--- |
| `Money` | 値オブジェクト | 金額を表す。不変で、金額が同じなら等しい。負の金額は作れない |
| `Stock` | エンティティ | 商品の在庫を表す。「足りるか」のルールを自分で持つ |
| `StockRepository` | リポジトリ | 在庫の保存先を隠す窓口。業務ルールは保存先を知らない |

### 値オブジェクトとエンティティ

| 種類 | 同じかどうかの基準 | 状態 | 例 |
| :--- | :--- | :--- | :--- |
| 値オブジェクト | 値が同じなら同じ | 不変 | 金額、住所、期間 |
| エンティティ | 識別子（ID）が同じなら同じ | 変化する | 在庫、注文、顧客 |

値オブジェクトは、**作った時点で正しい値であることを保証できます。** `Money` が負の値を拒否すれば、金額の検証をあちこちに書く必要がなくなります。

> **⚠️ よくある失敗・誤解**
> フィールドと `get` / `set` だけを持ち、ルールを何も持たないクラスは、ドメインモデルとは呼べません。実質的にはトランザクションスクリプトのままです。この状態は「貧血ドメインモデル」と呼ばれる、よくある失敗です。ルールを、オブジェクトの側へ移してください。

### 適用すると嬉しい状況・損をする状況

| 観点 | 内容 |
| :--- | :--- |
| 嬉しい状況 | 同じルールが複数の処理に現れる。ルールが複雑で、単体でテストしたい |
| 損をする状況 | ルールが少なく、処理も1〜2個。画面からデータベースへ、ほぼそのまま通すだけの処理 |
| 使わない選択肢 | トランザクションスクリプトのまま。**同じルールが2カ所に現れた時点** で、移行を考える |

### ステップ5: 注文処理を書き換える

`ExerciseOrderProcessor` を、`Money`、`Stock`、`StockRepository` を使う形に書き換えます。

- 金額計算の `int` を、`Money` に置き換えます。決済の上限判定も同様です
- 在庫は `repository` から取り出し、`reserve` して、`save` します
- 複数の明細があり、2番目の商品で在庫が足りなかったとき、1番目の商品の在庫はどうなりますか。分解前は、在庫が減らない仕様でした

## 解答例と解説

解答例の全文は [answers/ch07_domain_model/](../answers/ch07_domain_model/) にあります。自分で書き終えてから開いてください。

<details>
<summary>解答例の要点を見る</summary>

### Stock（ルールを自分で持つ）

```java
public void reserve(int amount) {
    // 「足りるか」のルールは、在庫自身が持つ
    if (amount > quantity) {
        throw new OutOfStockException("在庫が不足しています: " + productId);
    }
    quantity -= amount;
}
```

### Money（作った時点で正しい）

```java
private Money(int yen) {
    // 負の金額は作れない（不正な状態を、作った時点で防ぐ）
    if (yen < 0) {
        throw new IllegalArgumentException("金額は0円以上にしてください: " + yen);
    }
    this.yen = yen;
}
```

### 注文処理（薄い調整役）

```java
// 3. 在庫引当（足りるかの判断は Stock が行う。途中で足りなければ戻す）
List<OrderLine> reserved = new ArrayList<>();
try {
    for (OrderLine line : order.lines()) {
        Stock stock = repository.find(line.productId());
        stock.reserve(line.quantity());
        repository.save(stock);
        reserved.add(line);
    }
} catch (OutOfStockException e) {
    releaseAll(reserved);
    throw e;
}
```

### なぜこの切り方か

- 「在庫が足りるか」のルールを `Stock` に持たせたので、キャンセルや返品の処理でも、同じ `Stock` を使えます
- `Money` が不正な値を作らせないため、金額の検証が各所に散らばりません
- 保存先を `StockRepository` の裏に隠したので、データベースに替えるときは `InMemoryStockRepository` の代わりを書くだけです
- 注文処理は、取り出して、操作させて、保存するという「調整役」に徹しています。ルールの中身は知りません

</details>

## 他のパターンと比べる

| 比べる相手 | 違い |
| :--- | :--- |
| Layered（第8章） | この章は「ルールを何に持たせるか」。Layeredは「ルールを持つクラスを、どの層に置くか」。次の章で、この章の部品を層に配置する |
| Strategy（第2章） | Strategyは差し替える方式を切り出す。ドメインモデルは、概念ごとにルールを持たせる。両方を組み合わせる設計も多い |
| Hexagonal（第10章） | リポジトリは、Hexagonalの「ポート」の考え方につながる。業務ルールを保存先から独立させる点が共通している |

> **💼 現場Tip**
> 最初からドメインモデルで設計する必要はありません。まずトランザクションスクリプトで書き、**同じルールが2カ所に現れた時点で、そのルールだけをオブジェクトに移す** という進め方が、現実的で失敗しにくい方法です。

1. トランザクションスクリプトが向く場面と、向かない場面を、それぞれ説明してみましょう

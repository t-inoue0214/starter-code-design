# 第23章: 名前で意図を伝える（命名）

> この章の軸: すべての軸に共通（どのクラスの種類にも使う設計判断）

## この章のゴール

よくない名前が、なぜ読む人や直す人を困らせるのかを説明できるようになります。名前を直すと、なぜその困りごとが消えるのかも理解し、自分で名前を選べるようになります。

## Why: なぜ名前を設計として考えるのか

コードは、書く時間より、読まれる時間のほうがずっと長いものです。読む人が最初の手がかりとするのは、クラス、メソッド、変数の **名前** です。名前で意図が伝われば、中を読まずに済みます。伝わらなければ、呼び出すたびに中を読むことになります。

名前は、読みやすさだけの問題ではありません。**名前は、そのクラスやメソッドに「何を入れてよいか」を決める境界** にもなります。`CheckoutCalculator` という名前のクラスに、メールを送る処理を足そうとすれば、誰でも違和感を覚えます。名前が、責務の境界を守る見張りになるわけです。

[第19章](./19-immutability.md)では「変えられない」作りで、[第20章](./20-visibility.md)では「見えない」作りで、書いた人の意図を伝えました。この章で扱う名前は、意図を伝える一番身近な手段です。

## 前提

[第17章](./17-class-kinds.md)と[第18章](./18-business-classes.md)を読み終えていること。この章では、コードを書く課題はありません。実装例を読み、テストで違いを確かめます。

実装例は、[ch23_naming パッケージ](../src/main/java/com/example/orders/ch23_naming/)にあります。`before` パッケージには、名前の付け方が悪い実装を置いています。名前を直した実装と、**振る舞いはまったく同じ** です。

## 悪い実装を読む

[OrderManager.java](../src/main/java/com/example/orders/ch23_naming/before/OrderManager.java)と[OrderData.java](../src/main/java/com/example/orders/ch23_naming/before/OrderData.java)を開く前に、呼び出し側だけを読んでみてください。

```java
OrderManager manager = new OrderManager();
int x = manager.process(new OrderData("P", 10000, 3), true);
if (manager.check(data)) {
    // ...
}
```

次の問いに、呼び出し側だけを見て答えられるでしょうか。

- `process` は、何をするメソッドですか。戻り値の `x` は、何の金額ですか
- `true` は、何を意味していますか
- `"P"`、`10000`、`3` は、それぞれ何ですか。`10000` は税込みですか、税抜きですか
- `check` が `true` を返したら、何が成り立っているのですか

どれも、中を読まないと答えられません。中を読むと、`process` は「会員の割引と税を反映した支払額」を返し、`true` は「会員かどうか」でした。`check` は「取り消せるか」でした。名前を直した実装では、同じ呼び出しが次のように読めます。

```java
CheckoutCalculator calculator = new CheckoutCalculator();
int total = calculator.totalWithTax(new Order(OrderStatus.PLACED, 10000, 3), CustomerRank.MEMBER);
if (order.isCancellable()) {
    // ...
}
```

## 考え方: 困る名前と、直すと困りごとが消える理由

ここからは、よくない名前を種類ごとに見ます。それぞれ「何に困るか」「どう直すか」「なぜ直すと困りごとが消えるのか」の順に説明します。

### 1. 何でも入る名前（Manager、Data、Info、Util）

**困ること**: `OrderManager` には、注文に関係する処理なら何でも入れられます。金額の計算も、取消の判断も、メールの送信も、「注文を管理する」と言えてしまうからです。新しい処理を足す人は、迷わず `OrderManager` に足します。その結果、クラスは神クラスに育っていきます。

**直し方**: クラスの種類と役割が分かる名前にします。この章では、金額の計算を `CheckoutCalculator` に、取消の判断を `Order` に分けました。

**なぜ直るか**: 名前が、**入れてよいものの範囲を狭める** からです。`CheckoutCalculator` に入れてよいのは、支払額の計算だけです。メールを送る処理を足そうとすると、名前と中身が食い違います。この食い違いには、書いた本人とレビュアーの両方が気づけます。名前が具体的なほど、責務の境界がはっきりし、クラスが育ちすぎるのを防げます。

[第17章](./17-class-kinds.md)と[第18章](./18-business-classes.md)の種類の名前（`Service`、`Repository`、`Policy`、`Calculator` など）を、クラス名の最後に付けるのも、同じ理由です。種類の名前は、「このクラスは、どこまでやってよいか」を伝えます。

### 2. 何をするか分からない動詞（process、handle、execute、doSomething）

**困ること**: `process` は、どんな処理にも付けられる動詞です。呼び出し側に `manager.process(data, true)` と書かれていても、何が起きるのか分かりません。計算するだけなのか、保存もするのか、メールも送るのか、中を読むまで分かりません。

**直し方**: 何をして、何を返すのかが分かる動詞にします。`process` は `totalWithTax` になりました。

**なぜ直るか**: 呼び出し側を読むだけで、**何が起きて、何が返るのかが分かる** からです。`totalWithTax` という名前からは、「税込みの合計を返すだけで、保存やメールの送信はしない」と読み取れます。読む人は、中を開かずに先へ進めます。また、名前が1つの仕事を表すので、別の仕事を混ぜ込むと名前と合わなくなります。1の「何でも入る名前」と同じく、名前が見張りになります。

### 3. 状態を書き換えるだけの名前（setStatus）

**困ること**: 取り消しを `order.setStatus(CANCELLED)` と書くと、ただ値を書き換えているようにしか見えません。「出荷済みは取り消せない」という決まりを、呼び出す側が毎回、自分で確かめることになります。確かめ忘れた呼び出しが1つあれば、出荷済みの注文が取り消されます。

**直し方**: 業務の操作の名前にします。`setStatus(CANCELLED)` ではなく、`cancel()` にします。[第18章](./18-business-classes.md)の `PlacedOrder.cancel` が、この形です。

**なぜ直るか**: 業務の操作の名前にすると、**その操作の決まりを、メソッドの中に置ける** からです。`cancel()` の中で「取り消せる状態か」を確かめれば、呼び出す側は確かめる必要がなくなります。確かめ忘れの起きる場所は、1か所もなくなります。`setStatus` という名前では、中で取消の決まりを確かめるのは不自然です。「状態を書き換える」以外のことをしないと、名前が約束しているからです。

### 4. 何が真なのか分からない真偽の名前（flag、check、status）

**困ること**: `check(data)` が `true` を返したとき、何が成り立っているのか分かりません。「取り消せる」なのか、「問題がある」なのか、名前からは反対の意味にも読めます。読み違えると、`if` の条件を逆に書いてしまいます。

**直し方**: `is`、`has`、`can` で始まる、真になる条件そのものの名前にします。`check` は `isCancellable` になりました。

**なぜ直るか**: 名前が、**`true` の意味を1つに決める** からです。`isCancellable()` が `true` なら「取り消せる」以外の意味になりません。さらに、`if (order.isCancellable())` は「もし注文が取り消せるなら」と、そのまま文として読めます。条件を逆に書くと、文として読んだときにおかしくなるので、誤りに気づけます。

### 5. 意味の見えない boolean の引数（process(data, true)）

**困ること**: 呼び出し側の `true` は、何の `true` なのか分かりません。引数の名前（`flag`）は、メソッドの中にしか書かれていないからです。2つ並べて `process(data, true, false)` になると、順番を取り違えても、コンパイラは気づきません。

**直し方**: 意味のある Enum に置き換えます。`true` は `CustomerRank.MEMBER` になりました。

**なぜ直るか**: Enum にすると、**意味が呼び出し側に書かれる** からです。`CustomerRank.MEMBER` と書かれていれば、「会員として計算する」と読めます。型が違うので、別の引数と取り違えると、コンパイルエラーになります。さらに、あとから「ゴールド会員」を足すときも、Enum に1つ足すだけで済みます。`boolean` のままでは、2種類しか表せません。

### 6. 単位や範囲が分からない名前（amount、price、days）

**困ること**: `amt` という名前を見ても、税込みと税抜きのどちらなのか分かりません。税抜きの金額に税を足すつもりで、税込みの金額に、もう一度税を足してしまう誤りが起きます。`days` も、「何からの日数か」が分かりません。

**直し方**: 単位や範囲を、名前に含めます。`amt` は `subtotalBeforeTax`（税抜きの小計）に、戻り値は `totalWithTax`（税込みの合計）に、`days` は `daysSincePlaced`（確定してからの日数）になりました。

**なぜ直るか**: 取り違えたとき、**書いた行そのものが、おかしく読める** からです。`totalWithTax + tax` と書けば、「税込みに税を足している」と、書いた瞬間に気づけます。名前が `amt` のままなら、`amt + tax` は正しく見えてしまいます。もう一歩進めるなら、[第9章](./09-domain-model.md)の `Money` のように、型で区別する方法もあります。

### 7. 省略した名前（st、amt、a、x）

**困ること**: `st` が status なのか、street なのか、start なのか、書いた人にしか分かりません。読む人は、使われ方から推測するしかありません。推測を間違えると、直すべき箇所を間違えます。

**直し方**: 省略せずに書きます。`st` は `status` になりました。状態の値も、`"P"` という文字ではなく、`OrderStatus.PLACED` にしました。

**なぜ直るか**: 名前を読むだけで、**推測せずに意味が分かる** からです。省略して短くなる文字数より、読む人が推測にかける時間のほうが、ずっと高くつきます。今のエディタは名前を補完してくれるので、長い名前を書く手間も、ほとんどかかりません。

ただし、短い名前がいけないわけではありません。**名前の長さは、使われる範囲の広さに合わせます。** 3行で終わる `for` 文の `i` は、それで十分です。クラスのフィールドや、`public` なメソッドの名前は、使われる範囲が広いので、省略しません。

## まとめ: 直した名前が効く理由

| 困る名前 | 直した名前の例 | 直ると何が起きるか |
| :--- | :--- | :--- |
| `OrderManager`、`OrderData` | `CheckoutCalculator`、`Order` | 入れてよいものが狭まり、クラスが育ちすぎない |
| `process`、`handle` | `totalWithTax`、`place`、`reserve` | 呼び出し側だけで、何が起きて何が返るか分かる |
| `setStatus(CANCELLED)` | `cancel()` | 操作の決まりを、メソッドの中に置ける |
| `check`、`flag` | `isCancellable`、`hasStock` | `true` の意味が1つに決まり、`if` が文として読める |
| `process(data, true)` | `CustomerRank.MEMBER` | 呼び出し側に意味が書かれ、取り違えがコンパイルエラーになる |
| `amt`、`days` | `subtotalBeforeTax`、`daysSincePlaced` | 取り違えた行が、書いた瞬間におかしく読める |
| `st`、`a`、`x` | `status`、`discounted`、`total` | 推測せずに意味が分かる |

どの直し方にも、共通することがあります。**読むときや書くときに、誤りが目に見えてくる** ことです。よい名前は、誤りを防ぐというより、誤りを見つけやすくします。

## フレームワークや基盤のコードでは、汎用的な名前でよい理由

ここまで読むと、疑問がわくはずです。フレームワークには、`handle`、`execute`、`process` や、`TransactionManager` のような名前がたくさんあります。「この章では困る名前と言われたのに、フレームワークでは使ってよいのはなぜか」という疑問です。

答えは、1つの原則にまとめられます。**名前の具体性は、そのコードが知っている世界の具体性に合わせます。**

### フレームワークは、業務を知らない

フレームワークは、使う側の業務を知りません。自分が注文を扱うのか、予約を扱うのかを知らないので、業務の言葉で名前を付けられません。そのため、`handle` や `execute` のような汎用的な名前になります。

ただし、汎用的なのは「業務から見て」の話です。フレームワーク自身の仕事から見ると、名前は十分に具体的です。

| 名前 | 汎用的に見えるが、実は具体的なこと |
| :--- | :--- |
| `TransactionManager` | 管理する対象は、トランザクションだけ。何でも入るわけではない |
| `Runnable.run`、`Callable.call` | 「別のスレッドで動かす1つの仕事」という約束が、型で決まっている |
| `Comparator.compare` | 戻り値の意味（負、0、正）が、仕様で決まっている |

この章の `OrderManager` が困るのは、「注文に関係すること」という範囲が、業務の上でいくらでも広がるからです。`TransactionManager` の範囲は、技術の世界の中で閉じています。同じ `Manager` でも、入れてよいものの範囲が狭いかどうかで、良し悪しが分かれます。

### 自分のコードでも、知っている世界で決める

同じ考え方は、自分たちのコードにも当てはまります。

| 書いているコード | 知っている世界 | 名前の例 |
| :--- | :--- | :--- |
| フレームワーク、ライブラリ | 業務を知らない | `handle`、`execute`、`Filter` |
| 自分たちの基盤のコード（再試行、ログ、イベントの配送など） | 技術の仕組みだけを知る | `RetryExecutor.execute`、`EventDispatcher.dispatch` |
| 業務のコード | 業務を知っている | `place`、`cancel`、`reserve`、`totalWithTax` |

基盤のコードに `execute` と付けるのは、正しい判断です。どんな業務の処理を動かすのかを、基盤は知らないからです。反対に、業務のコードで汎用的な名前を選ぶと、知っているはずの意味を捨てることになります。業務のコードが汎用的な名前を避けるのは、この理由です。

### フレームワークに名前を決められたら、すぐ業務の名前に任せる

フレームワークのインターフェースを実装するときは、`handle(request)` のように、メソッドの名前が決められています。この名前は変えられないので、そのままで構いません。代わりに、**中ですぐ、業務の名前のメソッドに任せます。**

```java
@Override
public Response handle(Request request) {
    // 名前はフレームワークの約束。ここから先は、業務の言葉で書く
    return orderService.place(toCommand(request));
}
```

汎用的な名前は、フレームワークとの境界の1か所にとどめ、内側には広げません。この教材では、Controller やアダプターが、その境界に当たります（[第10章](./10-hexagonal.md)）。

### 具体性は、クラス名とメソッド名の組で決まる

`DiscountPolicy.apply` や、Strategy の `calculate` は、メソッド名だけを見ると汎用的です。しかし、クラス名が意味を補っているので、呼び出し側は `discountPolicy.apply(order)` と読めます。「割引の決まりを、注文に当てはめる」と分かります。

`OrderManager.process` が困るのは、組にしても意味が出てこないからです。メソッド名を短く汎用的にしたいときは、クラス名で十分に具体的にしておきます。

> **⚠️ よくある失敗・誤解**
> 「フレームワークが `process` を使っているから、自分の業務のクラスにも `process` を使ってよい」と考えるのは誤りです。フレームワークは業務を知らないから、汎用的な名前を選んでいます。業務を知っているコードが、それを真似る理由はありません。

## チームで名前をそろえる

1つずつの名前が良くても、チームでばらばらだと、読む人は迷います。

- **同じものには、同じ名前を使う**: ある場所では「注文」、別の場所では「受注」と呼ぶと、読む人は別のものだと考えます。用語集を短く作っておき、新しい言葉が出たら足していきます
- **業務の担当者の言葉を使う**: 担当者が「在庫を引き当てる」と言うなら、メソッドは `reserve` にします。会議の言葉とコードの言葉がそろうと、仕様の話をしながらコードを指せます。業務の言葉については、[第9章](./09-domain-model.md)でも触れています
- **Java の慣習に合わせる**: クラスは名詞、メソッドは動詞、真偽を返すメソッドは `is`、`has`、`can` で始める、定数はすべて大文字です。この教材では、アクセサに `get` を付けない決まりにしています。どちらを選んでも、チームの中でそろえることが大切です

> **💼 現場Tip**
> よい名前が思い付かないときは、責務がはっきりしていない合図です。名前を考える前に、「このクラスは、何を決めるのか」を1文で書いてみます。1文に「と」が何度も出てくるなら、クラスを分ける候補です。名前に `And` が入りそうなときも、同じ合図です。

## 名前を直すのは、安全なリファクタリング

名前を変えても、プログラムの振る舞いは変わりません。この章のテストは、名前の悪い実装と名前を直した実装に同じ入力を渡し、結果が同じになることを確かめています。

エディタの「名前の変更」の機能を使えば、呼び出している場所も、まとめて書き換えられます。テストが green のまま、名前だけを良くできます。**よい名前は、最初から付けるものというより、分かったときに付け直すもの** です。業務への理解が深まって、もっと良い名前が見つかったら、その時点で直します。

ただし、`public` な名前は、外の誰かが使っています（[第20章](./20-visibility.md)）。外部に公開している API の名前は、使っている人と相談して、時間をかけて変えます。

## 混同しやすい組み合わせ

| 組み合わせ | 違い |
| :--- | :--- |
| 長い名前 と 分かりやすい名前 | 長さは目的ではない。使われる範囲が広いほど、意味を省略せずに書く |
| 種類の名前 と 役割の名前 | `Service`、`Repository` は種類を伝える。その前の `Checkout`、`Order` は役割を伝える。両方そろって、中身が想像できる |
| コメント と 名前 | 名前で伝わることは、名前で伝える。コメントは、名前では伝えきれない「なぜ」を書く |

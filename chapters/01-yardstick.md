# 第1章: 良い分け方を判断する物差し

> この章の軸: すべての軸に共通（パターンを評価するための物差し）

## この章のゴール

神クラスを読み、「どこが、なぜ痛いのか」を凝集度・結合度・コードの臭いの言葉で説明できるようになります。この章ではコードを分解しません。第12章以降で使う評価の言葉を手に入れる章です。

## Why: なぜ物差しが先に必要なのか

第2章以降では、同じ神クラスを何度も別の形に分けます。そのとき「分けた結果、何が良くなったのか」を言葉にできないと、パターンを形だけ真似ることになります。

現場でも同じです。設計レビューで「ここは分けたほうがいいです」と言われたとき、理由を答えられなければ議論になりません。逆に、自分のコードの痛みを言葉にできれば、パターンの名前を知らなくても改善の方向が見えます。

## 前提

[第0章](./00-paradigms.md)を読み終えていること。Javaの基礎（クラス、インターフェース、例外）がわかっていること。

## 悪い実装を読む

次のファイルを開いてください。この章では読むだけで、編集はしません。

- [LegacyOrderProcessor.java](../src/main/java/com/example/orders/ch01_yardstick/before/LegacyOrderProcessor.java)

これは注文処理のすべてを1つのクラスに詰め込んだ、神クラスです。1つの `process` メソッドの中で、次のことを順番に行っています。

1. 入力検証
1. 金額計算（会員ランク、クーポン、季節の割引）
1. 在庫引当
1. 決済
1. 通知（メールとSMS）
1. 監査ログ

まず動作が正しいことを確認します。

```bash
mvn test
```

12件のテストが green になります。つまり、このクラスは正しく動きます。問題は動作ではなく構造にあります。

関連する型は [domain パッケージ](../src/main/java/com/example/orders/domain/) にあります。注文（`Order`）、注文者（`Customer`）、明細（`OrderLine`）などです。これらは全章共通の型であり、変更しません。

## 考え方

### 変更要求を想像する

コードの良し悪しは、読んだ印象ではなく、**変更要求が来たときに何カ所を触るか** で測れます。次の3つの変更要求が来たと想像してください。

- 法人向けの割引を足したい
- 通知にチャットツールを足したい
- 会員ランクにプラチナを足したい

触る箇所が1カ所なら、そのコードは変更に強い構造です。複数のカ所を触る必要があるなら、構造に問題があります。

### 凝集度と結合度

| 用語 | 意味 | 目指す状態 |
| :--- | :--- | :--- |
| 凝集度 | 1つのクラスの中身が、どれだけ同じ目的でまとまっているか | 高い（1つの目的に絞られている） |
| 結合度 | クラスどうしが、どれだけ互いの内部に依存しているか | 低い（窓口だけを知っている） |

神クラスは、凝集度が低く、結合度が高い状態です。検証、計算、在庫、決済、通知がバラバラの目的なのに、1つのクラスに同居しています。しかも、同じ変数（`total` や `order.customer()`）を通じて互いに絡み合っています。

### 変更理由で見る（単一責任）

クラスの責務を数える簡単な方法は、「このクラスを変更する理由はいくつあるか」を数えることです。

- 割引ルールが変わった
- 通知手段が増えた
- 決済会社の仕様が変わった
- 監査ログの書式が変わった

これらはそれぞれ別の人、別の時期に起きる変更です。1つのクラスが4つの理由で変更されるなら、責務が4つあることになります。

### SOLID原則（1行ずつ）

SOLIDは、結合度と凝集度を保つための5つの指針です。用語を覚えるより、問いの形で持つほうが役立ちます。

| 原則 | 問い |
| :--- | :--- |
| S: 単一責任 | このクラスを変更する理由は1つだけか |
| O: 開放閉鎖 | 機能を足すとき、既存のコードを書き換えずに済むか |
| L: リスコフの置換 | 親の型の代わりに子の型を入れても、呼び出し側は困らないか |
| I: インターフェース分離 | 使わないメソッドまで、呼び出し側に見せていないか |
| D: 依存関係逆転 | 業務の中心が、細かい実装（具体クラス）に直接依存していないか |

この教材では、第12章（Strategy）で O と D を、第13章（Observer）で S を、それぞれ体験します。

### コードの臭い

「臭い」は、悪いコードに共通する兆候の名前です。名前が付いていると、レビューで短く指摘できます。

| 臭いの名前 | 兆候 |
| :--- | :--- |
| 巨大クラス（神クラス） | 1つのクラスに責務が多すぎる |
| 長いメソッド | 1つのメソッドが長く、段落ごとにコメントが必要になる |
| if-else の連鎖 | 種類が増えるたびに分岐を足す |
| 変更の散弾（Shotgun Surgery） | 1つの変更で、複数の場所を同時に直す |
| 発散的変更（Divergent Change） | 無関係な理由で、同じクラスが何度も変更される |
| 基本型への執着 | 金額などの業務概念を、`int` や `String` のまま扱う |
| マジックナンバー | 意味の説明がない数値や文字列が埋め込まれている |

> **⚠️ よくある失敗・誤解**
> 臭いがあるからといって、必ず直すべきとは限りません。変更が起きないコードに、物差しを当てすぎて分割すると、読みにくくなるだけです。物差しは「直す判断」を助ける道具であり、「直す命令」ではありません。

## 課題: 神クラスを診断しよう

コードは書きません。ノートかメモ帳を用意して、次の3ステップで診断してください。

### ステップ1: 責務を書き出す

`process` メソッドを上から読み、段落ごとに「何の責務か」をメモします。そのうえで、次の問いに答えます。

- 責務はいくつありますか
- 責務どうしは、どの変数を通じてつながっていますか
- 外から見て、本来は独立しているのに、1つの流れに混ざっているものはどれですか

### ステップ2: 変更要求ごとに触る箇所を数える

先ほどの3つの変更要求について、ファイルの中のどの行を触ることになるか、メモします。

| 変更要求 | 触る箇所 |
| :--- | :--- |
| 法人向けの割引を足したい | （自分で書く） |
| 通知にチャットツールを足したい | （自分で書く） |
| 会員ランクにプラチナを足したい | （自分で書く） |

> **🔍 確認・実験してみよう**
> 試しに、会員ランクにプラチナを足す変更を、実際に手元で想像してみてください。`MemberRank` の他に、どの `if` を直す必要がありますか。直し忘れると、コンパイルエラーになりますか、それとも静かに割引なしになりますか。動かす前に予想してから確認してください。

### ステップ3: 臭いに名前を付ける

「考え方」の表を見ながら、このクラスに当てはまる臭いを探し、それぞれコード中の具体的な行を指してください。

### 責務の一覧

| 段落 | 責務 | 変更の理由 |
| :--- | :--- | :--- |
| 1 | 入力検証 | 業務ルールの変更 |
| 2 | 金額計算（会員ランク、クーポン、季節） | 営業施策の変更 |
| 3 | 在庫引当 | 在庫管理方式の変更 |
| 4 | 決済 | 決済会社や上限額の変更 |
| 5 | 通知 | 通知手段の追加 |
| 6 | 監査ログ | 監査要件の変更 |

少なくとも6つの責務があります。しかも金額計算の中には、会員ランク、クーポン、季節という3つの別々の割引ルールが同居しています。

### 変更要求ごとの触る箇所

| 変更要求 | 触る箇所 |
| :--- | :--- |
| 法人向けの割引 | 金額計算の `if-else` に分岐を足す。顧客の種別を持たせるため、`Customer` も触る |
| 通知にチャットツール | 通知の段落に分岐を足す。さらに `Customer` に連絡先を足す |
| プラチナ会員 | `MemberRank` に値を足す。割引の `if-else` に分岐を足す |

どれも、既存の `process` メソッドを直接書き換える必要があります。他の責務と同じメソッドの中なので、直したあとは全体のテストをやり直す必要があります。

### 臭いの一覧

| 臭い | 該当箇所 |
| :--- | :--- |
| 巨大クラス | クラス全体。6つ以上の責務 |
| 長いメソッド | `process` メソッド全体。段落ごとにコメントが必要なほど長い |
| if-else の連鎖 | 会員ランク、クーポンの種類による割引の分岐 |
| 変更の散弾 | 通知手段を足すときは、通知の段落と `Customer` の両方を直す |
| 発散的変更 | 営業、決済、監査、通知の担当者が、それぞれ同じクラスを変更する |
| 基本型への執着 | 金額が `int`、クーポンが `String` のまま |
| マジックナンバー | `500000`、`10000`、`"WELCOME500"`、`12`（月）、`10 / 100` など |

この診断は、第2章以降の設計に直結します。クラスの置き場所は第2章（役割分け）、長いメソッドは第3章、割引の `if-else` の連鎖は第12章（Strategy）、通知と監査ログは第13章（Observer）で扱います。

## 他のパターンと比べる

この章は特定のパターンではなく、パターンを比べるための共通の言葉を学ぶ章です。

物差しを当てすぎることにも注意が必要です。たとえば、検証のコードが10行で、今後も変更がないなら、無理にクラスを分ける必要はありません。**分ける判断は、変更の起きやすさで決めます。** 起きない変更のために分けると、クラスが増えるだけで、読む人の負担が増えます。

トランザクションスクリプト（処理を手続きで書く方式）は、小規模ならこの神クラスのままでも問題になりません。第3章で標準形を学び、第9章で規模が大きくなったときの限界を確認します。

> **💼 現場Tip**
> レビューでは「ここが気持ち悪いです」ではなく、「この変更のとき、2カ所を直す必要があります（変更の散弾）」と伝えると、相手が納得しやすくなります。

## もっと良くしてみよう

### 理解確認

1. 凝集度と結合度を、それぞれ1文で説明してみましょう
1. 「変更理由が複数あるクラス」とは、どういうクラスですか。身近なコードで例を探してみましょう
1. 「変更の散弾」と「発散的変更」の違いを説明してみましょう

### 発展改善クイズ

1. 神クラスの `process` メソッドに、上限額の判断（50万円）が直接書かれています。決済会社を2つ使い分けることになったら、どこをどう直すことになるでしょうか。自分なりに考えてみましょう
1. 臭いの一覧にある「基本型への執着」は、どう直せばよさそうでしょうか。後の章へ進む前に、方針だけ考えてみましょう
